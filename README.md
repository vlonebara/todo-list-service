# Планировщик задач Todo List

[![Проверки dev](https://github.com/vlonebara/todo-list-service/actions/workflows/ci.yml/badge.svg?branch=dev)](https://github.com/vlonebara/todo-list-service/actions/workflows/ci.yml?query=branch%3Adev)

Веб-приложение для личных задач: записать дело, назначить дату, настроить повторение и отметить выполнение. Одноразовая задача после выполнения удаляется, повторяющаяся переносится на следующую дату. История сохраняет прежние данные и позволяет отменить последние действия.

Сервер написан на Go, данные хранятся в SQLite, интерфейс работает на обычных HTML, CSS и JavaScript. Для фронтенда не нужны Node.js, Vite или сборщик.

Обновлённая версия находится в [ветке dev](https://github.com/vlonebara/todo-list-service/tree/dev). Эта инструкция описывает её возможности и настройки.

## Возможности

- создание, просмотр, изменение и удаление задач;
- страницы по 15 записей с кнопкой «Показать ещё»;
- поиск в заголовке и комментарии без учёта регистра, в том числе для русских букв;
- поиск по дате `DD.MM.YYYY`;
- фильтры «Сегодня», «Просроченные» и «Предстоящие»;
- ежедневные, ежегодные, недельные и месячные повторения;
- история создания, редактирования, выполнения и удаления;
- последовательная отмена последних действий;
- экспорт всех задач в JSON;
- напоминания сообщением и заголовком открытой вкладки;
- вход по паролю, JWT в защищённой cookie и выход;
- резервное копирование и восстановление SQLite;
- корректная остановка сервера по `SIGINT` и `SIGTERM`.

Это приложение для одного владельца с общим паролем. Отдельных пользователей и разграничения их задач нет.

## Быстрый локальный запуск

Нужен Go версии, указанной в [go.mod](./go.mod), или новее. Получить текущую версию проекта:

```bash
git clone --branch dev https://github.com/vlonebara/todo-list-service.git
cd todo-list-service
```

Следующие команды выполняются из корня проекта. Если `.env` уже существует, сохраните свои настройки и сравните их с [.env.example](./.env.example), пропустив копирование:

```bash
cp .env.example .env
go mod download
go run ./cmd
```

Откройте [http://localhost:7540](http://localhost:7540). Для завершения нажмите `Ctrl+C`.

Пример `.env`:

```dotenv
TODO_HOST=127.0.0.1
TODO_PORT=7540
TODO_DBFILE=./scheduler.db
TODO_PASSWORD=
TODO_JWT_SECRET=
TODO_COOKIE_SECURE=false
TZ=Europe/Moscow
```

Для включения входа задайте собственный `TODO_PASSWORD`. Файл `.env` содержит локальные настройки и исключён из Git. Не используйте реальные пароли в командах, которые сохраняются в истории терминала.

Приложение загружает `.env` один раз при запуске. Уже заданные переменные окружения имеют приоритет, включая пустые значения. Для применения настроек нужен перезапуск.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `TODO_HOST` | `127.0.0.1` | Адрес прослушивания |
| `TODO_PORT` | `7540` | Порт от 1 до 65535 |
| `TODO_DBFILE` | `scheduler.db` | Путь к SQLite |
| `TODO_PASSWORD` | пусто | Общий пароль; без него разрешён только loopback-адрес |
| `TODO_JWT_SECRET` | случайный ключ на время работы | Необязательный постоянный ключ, минимум 32 байта |
| `TODO_COOKIE_SECURE` | `false` для localhost, `true` для внешнего адреса | Передавать cookie только по HTTPS |
| `TZ` | часовой пояс ОС | Часовой пояс календарных операций сервера |

Для постоянного ключа JWT можно использовать `openssl rand -base64 32`. Если ключ не задан, после перезапуска нужно войти снова. Смена пароля также делает старые токены недействительными.

Относительный путь БД считается от рабочего каталога процесса. Каталог должен существовать. Сервер раздаёт `./web`, поэтому обычный запуск выполняется из корня проекта. Часовой пояс сервера и браузера владельца рекомендуется согласовать; пример использует `Europe/Moscow`. В бинарник включена база часовых поясов.

При первом запуске сервер создаёт файл БД и таблицы. В текущей версии репозитория готовая БД не поставляется: данные, резервные копии и локальный отчёт `CHANGES.md` исключены из Git через [.gitignore](./.gitignore). Старые коммиты могут содержать ранее отслеживаемую БД; историю Git это изменение не переписывает.

### Публичное размещение

Для внешнего адреса, например `TODO_HOST=0.0.0.0`, пароль обязателен. Перед приложением настройте HTTPS-прокси, сохраните исходный заголовок `Host` и задайте `TODO_COOKIE_SECURE=true`. HTTPS завершается на прокси; сам Go-сервер принимает HTTP внутри доверенной сети.

Cookie использует `HttpOnly`, `SameSite=Strict`, срок жизни 8 часов и `Secure` согласно настройке. Запросы изменения данных проходят стандартную CSRF-защиту Go. Выход удаляет cookie текущего браузера. Уже скопированный JWT остаётся действительным до истечения срока; для принудительного сброса всех токенов замените ключ JWT и перезапустите сервер.

Вход ограничен пятью попытками в минуту с адреса соединения и ста попытками в минуту суммарно. Заголовки `X-Forwarded-For` не считаются доверенными. Если нужен отдельный лимит клиентов за прокси, настройте его на прокси.

## Запуск тестов

Тесты сами создают временную БД, запускают HTTP-сервер на свободном порту и получают свежий JWT. Рабочая БД и уже запущенный сервер им не нужны. Переданные `TODO_PORT` и `TODO_DBFILE` не направляют эти тесты в рабочую установку.

```bash
go test ./tests -v
go test ./... -count=1
go test -race ./... -count=1
go vet ./...
```

Отдельный сценарий:

```bash
go test ./tests -run '^TestDelTask$' -v
```

Модульные проверки находятся рядом с кодом в [pkg](./pkg). Интеграционные сценарии — в [tests](./tests). Проверяются календарные границы, ошибки API, cookie и CSRF, миграции, поиск, конкурентное завершение, откат истории и восстановление копии.

Проверка известных уязвимостей:

```bash
go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
```

## Docker

Сначала задайте собственный `TODO_PASSWORD` в `.env`. Для Docker он обязателен: приложение слушает внешний интерфейс контейнера.

```bash
docker build --pull -t todo-list:local .
docker volume create todo-data
docker run -d --name todo-list \
  --env-file .env \
  -e TODO_HOST=0.0.0.0 \
  -e TODO_PORT=7540 \
  -e TODO_DBFILE=/data/scheduler.db \
  -e TODO_COOKIE_SECURE=false \
  -p 127.0.0.1:7540:7540 \
  -v todo-data:/data \
  todo-list:local
```

Этот пример предназначен для локального HTTP-доступа. Для публичного HTTPS-сайта используйте `TODO_COOKIE_SECURE=true` и прокси. Настройки `TODO_HOST`, `TODO_PORT` и `TODO_DBFILE` в команде задают адрес, порт и путь внутри контейнера независимо от локального `.env`.

Контейнер запускается от пользователя `todo` с UID/GID `10001`. Именованный том сохраняет БД при пересоздании контейнера. Если вместо него привязываете каталог хоста, предоставьте UID `10001` право записи в этот каталог. Проверка `HEALTHCHECK` обращается к `/api/health`.

```bash
docker logs -f todo-list
docker stop todo-list
docker start todo-list
```

При обновлении соберите новый образ и пересоздайте контейнер с тем же томом и настройками. Сначала сохраните резервную копию БД. Откат приложения после изменения версии схемы выполняется вместе с восстановлением совместимой копии БД.

## Резервное копирование

Сохранить согласованную копию можно без остановки сервера:

```bash
mkdir -p backups
go run ./cmd -backup ./backups/scheduler-2026-11-11.db
```

Копирование использует SQLite `VACUUM INTO`, поэтому включает задачи, историю и версию схемы. Новый файл доступен только владельцу. Существующий файл не перезаписывается. Считайте копию готовой только после успешного завершения команды.

Восстановление выполняется в **новый** файл:

```bash
TODO_DBFILE=./restored.db go run ./cmd -restore ./backups/scheduler-2026-11-11.db
TODO_DBFILE=./restored.db go run ./cmd
```

Перед восстановлением проверяется целостность SQLite и наличие таблицы задач. Команда откажет, если целевой файл существует. Сначала проверьте восстановленный экземпляр, затем выберите его в настройках приложения. Копии содержат данные задач, поэтому храните их вне публичного доступа и репозитория.

## Архитектура

| Каталог | Ответственность |
| --- | --- |
| [cmd](./cmd) | Загрузка настроек, сборка зависимостей, команды копирования |
| [pkg/config](./pkg/config) | Однократное чтение конфигурации |
| [pkg/handlers](./pkg/handlers) | HTTP, маршруты, JSON, cookie, middleware и статические файлы |
| [pkg/service](./pkg/service) | Проверка данных, календарные правила и сценарии задач |
| [pkg/db](./pkg/db) | SQL, транзакции, миграции, история и резервные копии |
| [pkg/model](./pkg/model) | Независимые модели, фильтры и ошибки |
| [pkg/errutil](./pkg/errutil) | Общая проверка наличия ошибки через `CheckError` |
| [pkg/server](./pkg/server) | Запуск, таймауты и graceful shutdown |
| [web](./web) | Читаемый интерфейс без этапа сборки |
| [tests](./tests) | Изолированные интеграционные тесты |

Обработчики обращаются к сервисам через интерфейсы. Сервисы используют интерфейс хранилища; конкретный SQLite-адаптер создаётся в [main.go](./cmd/main.go). Один общий пул `*sql.DB` открывается при запуске, переиспользуется запросами и закрывается после остановки сервера. Контекст запроса передаётся до SQL.

Для каждого изменения задача и снимки истории записываются одной транзакцией. Завершение дополнительно проверяет, что прочитанная задача не изменилась другим запросом; при конфликте клиент получает `409` и должен обновить данные. Отмена восстанавливает последний неотменённый снимок. Изменения, внесённые напрямую в БД в обход API, могут помешать безопасной отмене.

Версии схемы хранятся в `PRAGMA user_version`. Первая миграция создаёт прежнюю таблицу `scheduler` и индекс по дате, вторая — `task_history`. Старая БД обновляется без удаления задач. Данные, записанные до появления истории, не получают историю задним числом.

## HTTP API

При локальном запуске базовый адрес — `http://localhost:7540`. Тела `POST /api/signin`, `POST /api/task` и `PUT /api/task` должны быть JSON-объектами с `Content-Type: application/json`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/health` | Готовность сервера и БД |
| GET | `/api/session` | Необходимость входа и состояние cookie |
| POST | `/api/signin` | Вход по паролю |
| POST | `/api/signout` | Удаление cookie браузера |
| GET | `/api/nextdate` | Расчёт следующей даты обычным текстом |
| POST | `/api/task` | Создание задачи |
| GET | `/api/task?id=1` | Получение задачи |
| PUT | `/api/task` | Редактирование задачи |
| DELETE | `/api/task?id=1` | Удаление задачи |
| POST | `/api/task/done?id=1` | Выполнение задачи |
| POST | `/api/task/undo` | Отмена последнего действия |
| GET | `/api/tasks` | Страница задач |
| GET | `/api/tasks/export` | Все задачи как файл `tasks.json` |
| GET | `/api/history` | Страница истории |

Все операции с задачами, экспортом и историей требуют cookie `token`, если пароль включён. Служебные маршруты состояния, входа и расчёта даты доступны без токена.

### Вход

```json
{"password":"your-password"}
```

Успешный ответ содержит `{"token":"<jwt>"}` и `Set-Cookie`. Интерфейс использует cookie, установленную сервером. Пример для консольного клиента: отправьте JSON из подготовленного файла и сохраните cookie через `curl --cookie-jar`, затем передавайте её через `curl --cookie`.

### Задача

```json
{
  "id": "185",
  "date": "20300201",
  "title": "Подвести итог",
  "comment": "Подготовить отчёт",
  "repeat": "d 5"
}
```

`id` нужен для редактирования; при создании он выдаётся сервером. Все пять полей задачи возвращаются строками. Заголовок обязателен и ограничен 200 символами, комментарий — 5000, правило повторения — 128. Максимальный JSON-запрос — 1 МиБ. Поисковая строка ограничена 256 символами.

Дата имеет формат `YYYYMMDD` (`20060102` в Go), поддерживаются годы от 1 до 9999. Пустая дата заменяется текущей. Просроченная одноразовая задача назначается на сегодня; для повторяющейся рассчитывается следующее выполнение. Правило проверяется даже для будущей даты.

Создание возвращает `{"id":"185"}`. Успешное изменение, выполнение, удаление и отмена возвращают `{}`. Список и экспорт возвращают `{"tasks":[...]}`, в том числе `{"tasks":[]}`.

### Поиск, фильтры и страницы

```text
/api/tasks?search=бассейн&page=1
/api/tasks?search=08.02.2024
/api/tasks?period=today&page=1
/api/tasks?period=overdue
/api/tasks?period=upcoming
```

Параметры поиска нужно кодировать для URL. `search` ищет буквальную подстроку в заголовке и комментарии; корректная дата `DD.MM.YYYY` выбирает задачи на эту дату. `period` принимает `all`, `today`, `overdue`, `upcoming`. Поиск и период можно объединять. `page` начинается с 1; каждая страница содержит до 15 записей. Сортировка — по дате, затем ID.

Поиск русских букв выполняется средствами Go, поскольку обычный SQLite `LIKE` не обеспечивает нужное изменение регистра кириллицы. Записи читаются по порядку до заполнения нужной страницы. Для личного планировщика это сохраняет простую реализацию без отдельного поискового движка.

### Повторения

| Правило | Значение |
| --- | --- |
| пустая строка | Одноразовая задача |
| `d N` | Каждые N дней, от 1 до 400 |
| `y` | Каждый год |
| `w 1,4,5` | Понедельник, четверг, пятница; диапазон 1–7 |
| `m 1,15` | Первое и пятнадцатое число |
| `m -1` | Последний день месяца |
| `m -2` | Предпоследний день месяца |
| `m 1,-1 2,8` | Первый и последний дни февраля и августа |

`GET /api/nextdate` принимает `date`, `repeat` и необязательный `now` в формате `YYYYMMDD`. При отсутствии `now` используется текущая дата сервера. Результат строго позже `now`; интервал всегда отсчитывается от исходной даты с хотя бы одним переносом.

```text
/api/nextdate?now=20240126&date=20240113&repeat=d%207
```

Ответ: `20240127`. Переход 29 февраля при ежегодном повторении сохраняет поведение Go: следующий год даёт 1 марта.

### История и отмена

`GET /api/history?page=1` возвращает объект с массивом `history`. Запись содержит строковый `id`, `action` (`add`, `edit`, `complete`, `delete`), снимки `before` и `after`, время `created_at` в RFC3339 UTC и признак `undone`. Отсутствующий снимок равен `null`.

`POST /api/task/undo` отменяет последнее неотменённое действие. Следующий вызов отменяет предыдущее. История сохраняется и после отмены. Старую запись, поверх которой неизвестным способом изменили задачу, сервер не перезаписывает.

### Ошибки

```json
{"error":"task not found"}
```

| Код | Причина |
| --- | --- |
| 400 | Неверные данные, дата, правило или JSON |
| 401 | Неверный пароль или недействительная cookie |
| 403 | Заблокирован межсайтовый запрос или чужой Host в локальном режиме |
| 404 | Нет задачи или действия для отмены |
| 405 | Метод не поддерживается; разрешённые указаны в `Allow` |
| 409 | Задача изменилась другим запросом |
| 413 | Превышен размер JSON |
| 415 | Неверный тип содержимого JSON-запроса |
| 429 | Превышен лимит входа; повтор через `Retry-After` |
| 500 | Внутренняя ошибка; подробности остаются в логе |
| 503 | Проверка готовности БД не прошла |

Исключение — `/api/nextdate`: дата и ошибки возвращаются обычным текстом. Сообщения приложения об ошибках написаны на английском и начинаются с маленькой буквы.

## Автоматические проверки

[GitHub Actions](./.github/workflows/ci.yml) выполняет форматирование, `go vet`, тесты с детектором гонок, сборку и `govulncheck`. Отдельная задача собирает Docker-образ, проверяет запуск, готовность БД и непривилегированного пользователя, затем сканирует образ через Trivy. Проверка образа блокирует известные HIGH/CRITICAL-уязвимости, для которых уже есть исправления.

CI выполняется для `dev`, `main` и pull request в `main`. Тестовые контейнеры используют учебный пароль и удаляются после проверки. Размещение приложения и публикация образов этим workflow не выполняются.
